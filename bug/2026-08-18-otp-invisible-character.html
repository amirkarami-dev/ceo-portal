One engineer could never log in with the SMS code

Found 2026-08-18, 13:45 Tehran time · Fixed the same day, 14:05 · Engineer 2850159816

The code in the SMS was right. He put it in. The site still said the code was wrong or too old. It happened every single time, and only to him. Every other engineer could log in with no trouble.

What was wrong

When you copy a code from an SMS app, a hidden character comes with it. You cannot see it. It takes no space on the screen. But it makes the code one character longer — and the server checks the length first, so it says no before it even looks at the numbers.

Code the server made
44655 · 5 long
Code in the SMS
44655 · the same
Code the server received
44655‏ · 6 long

Why only one person

Other engineers type the code with their fingers. This one copied it. That was the whole difference.

It also made the bug hard to find. His account, his phone number, his membership and the SMS were all fine — because none of them were the problem.

The technical reason

The code that cleans user input changed Persian numbers into English numbers, but let every other character through. Trim() removes spaces, but a hidden mark is not a space. 

// This check compares LENGTH before it compares content.
CryptographicOperations.FixedTimeEquals(
    Encoding.UTF8.GetBytes(stored),      // "44655"  → 5 bytes
    Encoding.UTF8.GetBytes(code.Trim())  // "44655‏" → 8 bytes
);                                       // ⇒ false, and nothing is written down

The national code box had the same problem. There it showed a different message: “the national code must be 10 digits”.

How it was found

  • Is his record turned off in the engineering system? No. Active, licence valid until 1406/11/15.
  • Is his phone number old or different? No. Both databases hold 0918•••4273.
  • Is he blocked by a send limit? No. The server wrote no warning of any kind.
  • Does the SMS arrive, and is it our code? Yes, it arrives. Five digits, our wording, and it matched what the server stored.
  • Did the code run out of time? No. It failed even when sent once and used straight away.
  • Copy versus type. Found it. The same code failed when copied and worked when typed by hand.

What was changed

  • Only numbers are kept. Anything else, including hidden marks, is thrown away. This covers both the code box and the national code box.
  • The server now writes down why a code was refused. Before, “too old”, “wrong” and “never sent” all looked the same and left no trace.
  • The SMS service's answer is now read. It replies “200 OK” and puts the real result inside the message body, which was being thrown away.
  • A code now lives 5 minutes instead of 2. His SMS took over a minute to arrive, so he had about 45 seconds to use it.

Proof after the fix

A wrong code was sent on purpose, with the hidden mark attached, on the live server:

msgway accepted the send: {"status":"success","error":null,"referenceID":"1787048913621852686"}

OTP verify failed: code did not match
  (stored 5 chars, supplied 5)   ← the browser sent 6, the server got 5

The hidden mark is now removed. A national code with a hidden mark is also accepted.

What to remember

If a check compares length first, then anything a person might copy must be cleaned down to what you expect — not just trimmed. And any step that can fail quietly must write down why. Without that line, this took database queries and four live logins to find. With it, one minute.
