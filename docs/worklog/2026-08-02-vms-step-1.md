# VMS step 1 — one camera, end to end

- **Date:** 2026-08-02
- **Area:** VMS (`vms.myceo.ir`) — new service, design phase
- **Branch / commits:** `main`
- **Status:** **done.** go2rtc on the VPS plays the camera in a browser. No application code written yet.

## What step 1 had to answer

> *Confirm one camera end to end: find the RTSP path, main + substream, and how many sessions it
> tolerates. Done when go2rtc on the VPS plays one camera in a browser.*

All four answered. Three of them contradicted the design, so
[`2026-08-01-vms-service-design.md`](../superpowers/specs/2026-08-01-vms-service-design.md) has been
rewritten in place with the corrections marked.

## The stream URL

```
rtsp://admin:<password>@78.39.233.70:554/mode=real&idc=1&ids=1     main  H.265 2560x1440  9 fps  ~11.2 Mbit/s
rtsp://admin:<password>@78.39.233.70:554/mode=real&idc=1&ids=2     sub   H.265  704x576   9 fps  ~354 kbit/s
rtsp://admin:<password>@78.39.233.70:554/mode=real&idc=1&ids=4     jpeg  RTP/JPEG, unconsumable
```

The `Authorization: Basic` header is required — URL userinfo alone returns 401. go2rtc and ffmpeg
both send it automatically; a hand-rolled client will not.

### It could not have been guessed, and that is the reusable part

51 candidate paths across four sweeps, all 400. The reason is that **neither RTSP verb
discriminates** on this stack:

| Verb | Real path | Nonsense path |
|---|---|---|
| `OPTIONS` | 200 | **200** — `/nonsense-zzz` too; the URI is ignored |
| `DESCRIBE` | 200 | **400** — never 401, never 404, with or without credentials |

The design had predicted this would need "one credentialled probe". It needed the credential *and* a
different method entirely: **reading the camera's own web UI**. `http://<cam>/js/Common.js` holds
`geturlStr()`, which builds the URL the device's own player uses. The same function emits a `quii://`
scheme for its ActiveX viewer — which is where the `QV RTSP Server` banner comes from. The login page
also gives the family away: `var loginPort = 34567` is the Xiongmai signature.

**For the other seven cities: read `js/Common.js` first.** It cost four wasted sweeps to learn that.

## The finding that changes the product

**The camera site's own internet upload is ~0.41 Mbit/s.** Measured three times over plain HTTP with
no RTSP involved — a 161 KB file served by the camera itself, at 51.3 / 51.5 / 50.6 KB/s, RTT 58 ms,
0 % loss.

| Stream | Needs | Realtime factor achieved |
|---|---|---|
| main, 2560×1440 | ~11.2 Mbit/s | **0.045** — ffmpeg took 330 s to pull 15 s of video |
| sub, 704×576 | ~354 kbit/s | **~0.95** — 40 s of media in 42 s of wall clock |

So:

- **The main stream is unviewable from this site.** Not in a grid, not fullscreen, not for one person.
- **The substream works, with no headroom** — ~354 kbit/s against ~410 available is 86 % of the link.
  A second concurrent puller breaks both.
- **The VPS was never the constraint.** The design's whole §2.2 bandwidth table was built on the
  VPS's 44–62 Mbit/s upload. Twenty cameras is ~8 Mbit/s inbound. The wall is at the cameras.

This is the same shape of error as the room service's "500 Mbps" estimate: a number assumed from the
component we control rather than measured at the component that actually limits things.

## Two other assumptions overturned

**"These cameras cannot serve many viewers."** Wrong — **12 concurrent PLAY sessions held with no
refusal**, and the test stopped at 12 only because the loop did. The gateway is still mandatory, but
for the uplink's sake (one puller per camera), not the session count's.

**"H.264 passthrough, so no transcoding cost."** The cameras are **H.265**. That rules out WebRTC
(Chrome does not do HEVC over WebRTC) and leaves MSE as the only transport — which happily is what
the design already recommended, and it means **UDP 8555 never needs forwarding**.

## Verified in a browser

go2rtc 1.9.14 (`sha256 32d616af226bd731678ffde328b94cfb94e30339bfefc469cfb76323144615a6`) on the VPS
at `~/vms`, bound to `127.0.0.1:1984`, reached over an SSH tunnel — nothing was exposed publicly.

- Chromium 148 on Windows reports `hvc1` **and** `hev1` supported in MSE.
- `cam_sub` played **23 seconds continuously**, 4.0 s buffered, 0 dropped frames, 1024×576 display.
- A canvas grab off the `<video>` element returned a real picture — full luminance range, not a black
  frame. (`framesDecodedIn10s` read 0 only because the browser pane was hidden and Chromium suspends
  compositing; `drawImage` still decodes, which is how the check was made.)
- ffmpeg on the VPS grabbed the same frame independently: a stairwell, OSD `1405-05-11 14:44:38`,
  channel «دوربین ۱».

## Handling of the camera password

It was never typed into a command, a file, or a log. Amir set `VMS_CAM_PASS` as a User-scope
environment variable; a helper reads it and passes it as **line 1 of ssh stdin**, consumed by bash's
`read` builtin before `bash -s` starts — so it is never a process argument on the VPS. Every script
masks it out of its own output. `~/vms/go2rtc.yaml` on the VPS holds it, `chmod 600`, exactly as the
design's §4 specifies.

One thing to know: **go2rtc's `/api/streams` echoes the source URL including the password.** Another
reason the API must never be reachable without the forwardAuth of step 5.

## Left running on the VPS

`~/vms/go2rtc` under `nohup` with `~/vms/go2rtc.yaml` (chmod 600), listening on `127.0.0.1:1984`
only. It does not survive a reboot and is not a service yet — **step 4 makes it one**. ffmpeg was
installed on the VPS as an independent RTSP client; it stays, because it is the fallback if H.265
transcoding is ever needed.

## Follow-ups

- **Measure the uplink at two or three more sites before step 2.** If ~0.41 Mbit/s is typical, the
  product is a wall of 704×576 tiles and main-stream viewing never happens. If this site is just bad,
  the design's original shape survives. This is the most important open question.
- **Ask whether the cameras can be set to H.264, and the substream capped to ~250–300 kbit/s.** H.264
  removes the hardware-decoder risk; the cap gives the substream headroom instead of 86 % occupancy.
- **Confirm HEVC plays on the admins' actual machines** — it needs a hardware decoder, and a machine
  without one shows a black tile.
- **Does each site have its own credential?** Only one camera has been seen. Step 3's CRUD should
  assume per-camera, not global.
- The camera dropped off the internet for under 15 seconds mid-session (100 % packet loss, then back).
  It followed a burst of 12 concurrent sessions plus several ffmpeg pulls, so **it may well have been
  my load** rather than the site. Worth keeping in mind: these are low-end devices on thin links.
