## Three decisions worth the words

### 1. Cities are a table, not a C# enum — and not a display map either

The design said "a code with a display map, not a C# enum … adding a ninth city must be a row, not a
deployment." Those two halves contradict each other: a C# display map still needs a release. Since
the point was the second half, cities became **`VmsCities`**, seeded with the eight, and
`Camera.CityCode` is a real foreign key to `VmsCity.Code`.

That is a stronger guarantee than the `ReshteNames` pattern it was modelled on. `Reshte` degrades an
unknown code to «رشتهٔ ۸»; here the database refuses an unknown city outright. A camera with a bad
city code would not be *ugly*, it would be **invisible** — present in the table and absent from every
filter — so refusing the write is better than rendering it.

The FK is `Restrict`, not `Cascade`: removing a city from the picker must never delete the cameras
standing in it.

### 2. The password is not in the database, and the schema is what says so

`Camera` carries `CredentialKey` — a name like `default` — and the actual password lives only in a
file on the media VPS. Step 4 joins the two to generate go2rtc's config, so `CeoDb` can describe
every camera and open none of them. A backup, a stray query, or an over-broad API response cannot
leak a camera.

The design already promised this in prose. `No_password_column_exists_on_the_camera_table` reads the
EF model and fails on any property whose name contains "password" or "secret", so a future "just add
a password field" trips a test rather than a review.

### 3. `MainStreamId` is nullable, and null is a fact rather than a gap

Step 1 measured the site's uplink at ~0.41 Mbit/s against a main stream of ~11.2 Mbit/s. The main
stream is not merely expensive there — it cannot be watched. So null means *this site cannot carry
the main stream*, and a value means it has been measured and it can. Camera 1 is null.

`CK_VmsCameras_StreamsDiffer` refuses `MainStreamId = SubStreamId`. If those were equal, "fullscreen
switches to the main stream" would open a second session against a link with room for exactly one,
and the symptom would look like the camera dropping out rather than like a config mistake.

## Verification

- **Unit 333 passed.** **Functional 156 passed / 3 failed.**
- The three failures are `ShouldSaveAndReadBackAssessment`, `LegacyAudience_GetProjects_Returns200`
  and `UserToken_AdminEndpoint_Returns403`. **Confirmed pre-existing rather than assumed:** stashing
  every change and running just those three on a clean tree still fails all three.
- The 11 new tests are functional, not unit, on purpose — every rule they check is a CHECK
  constraint, a FK or a unique index, and an in-memory provider ignores all three. That is precisely
  how `CK_Rooms_JoinTokenMatchesMode` reached production able to refuse a soft delete.
- **The migration was applied to the populated local `CeoDb`**, not only to a fresh test database.
  Worth doing separately: a migration that is clean against an empty schema can still fail against
  one with data. All five CHECK constraints are present in `sys.check_constraints`, and
  `COL_LENGTH('VmsCameras','Password')` is NULL.

## Notes for the next step

- **`dotnet ef` with `--no-build` silently uses stale binaries.** It produced an *empty* migration,
  and later reported `database update` "Done" having applied nothing — `migrations list` did not even
  show the migration. Build the **startup** project after every model change. Added to GOTCHAS.
- Nothing is deployed. The API on production has no `VmsCameras` table until step 9.
- Step 3 (admin CRUD) should let the admin pick `CredentialKey` from the keys that actually exist on
  the VPS, rather than typing one; a typo there produces a camera that fails to connect for a reason
  no message will explain.
- Still open from step 1, and it gates how much of this matters: **is ~0.41 Mbit/s typical of every
  site?** Two or three more camera IPs would settle it.
