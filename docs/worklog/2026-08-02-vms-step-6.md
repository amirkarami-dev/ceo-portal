## The gateway is now one path wide

`Host(cam.myceo.ir) && Path(/api/ws)`. From the public internet, with a valid media cookie:

| Path | Before | Now |
|---|---|---|
| `/api/ws` (websocket upgrade), cookie | — | **101 Switching Protocols** |
| `/api/ws`, no cookie | — | **401** |
| `/api/streams` | **200 — returned the camera password** | **404** |
| `/api/config`, `/api/restart`, `/` | 200 | **404** |

Not "forbidden" — **unrouted**. Traefik has nowhere to send them, so the check happens before any
middleware and there is no configuration mistake that could re-open them by accident.

That closes the residual risk step 5 recorded. `/api/frame.jpeg` is 404 too; step 8 will want it for
thumbnails and should add it then, deliberately, rather than leaving the door open now.

## The player

Its own MSE-over-WebSocket client (`CameraPlayer.tsx`) rather than go2rtc's `video-stream.js` —
loading that script would mean serving JavaScript from the media host, which is exactly the surface
just narrowed away. Speaking the protocol directly keeps `cam.myceo.ir` to data only.

Three things in it are not cosmetic:

- **It offers H.265 first, filtered by `MediaSource.isTypeSupported`.** A machine with no hardware
  HEVC decoder does not offer it, so the gateway can answer with something else rather than sending
  frames nothing can decode.
- **A tile connects only when it is on screen and the tab is visible** (IntersectionObserver +
  `visibilitychange`). A connected tile is a live pull from a site with room for **one** puller at
  ~0.41 Mbit/s, so this is bandwidth control, not a nicety.
- **It jumps to the live edge** when the buffer runs more than 5 s ahead, and trims behind the
  playhead. A wall left open all morning otherwise drifts into replaying old footage while growing
  without limit.

Nine tiles a page, for the same reason. Paging is what stops a hundred cameras being opened because
somebody scrolled.

## Honest UI decisions

- **The wall is behind `RequireAdmin`, not just the management screens.** Unlike election-web and
  room-web there is no second, lighter audience — the design settled that only administrators watch.
- **Fullscreen shows the same substream, bigger, and says so.** Somebody will expect a sharper
  picture; the modal states plainly that the site's bandwidth does not allow the main stream. Better
  a sentence than a feature that looks broken.
- The camera form warns that a `CredentialKey` the media server does not hold produces a camera with
  no picture, because that failure is reported only in a log on another machine.

## What I could not verify

**I have not seen a single screen of this app signed in.** Every route is Administrator-only, so
reaching the wall needs an OIDC login, and I do not complete password logins. What was verified:

- `npm run typecheck`, `npm run lint --max-warnings 0` and `npm run build` all clean.
- The app **boots in a real browser**: correct title, `dir="rtl"`, `lang="fa"`, and it redirects to
  `/login` as designed. That exercises the whole module graph, which is what catches a bad import.
- **No horizontal overflow at 375 px** or at 1270 px.
- The browser's own codec probe reports `hvc1` supported — the machine that would be watching can
  decode what the cameras send.
- The gateway contract the player depends on is proven separately, above: a WebSocket upgrade to
  `/api/ws?src=baneh-01` returns **101** with a cookie and **401** without.

**So the untested thing is the assembled screen** — that tiles lay out, that the city filter narrows
the list, that a tile actually paints. Amir signing in once at step 9 settles all of it in a minute.
