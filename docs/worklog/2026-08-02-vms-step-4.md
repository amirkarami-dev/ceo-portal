# VMS step 4 — go2rtc's config comes from the database

- **Date:** 2026-08-02
- **Area:** VMS — `src/Application/Vms`, `src/Web/Endpoints/Vms`, `scripts/`, `deploy/vms/`, the media VPS
- **Branch / commits:** `main`
- **Status:** **done, and proven end to end.** go2rtc runs as a systemd service on the VPS and its
  config is generated. The API half is **not deployed** — production gets it with step 9.

## Criterion

> *go2rtc config generated from the database. Done when adding a camera does not mean hand-editing
> YAML — and any `CredentialKey` the VPS does not hold is reported, not silently written.*

Both halves demonstrated against the real API and the real camera. See **Proof** below.

## Shape: the VPS pulls, nothing is pushed

```
CeoDb ──► api.myceo.ir /api/VmsGateway/config ──► vms-sync on the VPS ──► /srv/vms/go2rtc.yaml
                     (streams block,                    ▲
                      {{cred:key}} placeholders)        │
                                          /srv/vms/credentials.env  (never leaves the VPS)
```

The direction is the whole point. Camera passwords live only on the media machine, so **nothing
sensitive travels and the API never needs a way in there.** Three owners, cleanly split:

| | Owner |
|---|---|
| `/srv/vms/base.yaml` — listen addresses, logging | the VPS |
| `/srv/vms/credentials.env` — `key=user:password`, 600 root | the VPS |
| the `streams:` block | the database |

## Decisions

### The YAML is rendered in C#, not in the shell script

`Go2RtcConfig.Render` is pure and unit-tested. The RTSP path spelling —
`/mode=real&idc=N&ids=M` — could not be guessed; 51 candidates all returned 400 and the real one had
to be read out of the camera's own JavaScript. **It must exist in exactly one place, under test, and
never be retyped in a shell script.** The script does one job the API cannot: substituting a
credential it alone holds.

### Credentials are placeholders, and URL-encoded on substitution

The API emits `rtsp://{{cred:default}}@host:554/…`. The agent replaces it with
`user:urlencoded-password`. The encoding is not cosmetic: the camera password contains `@`, which
would otherwise split the URL, and an apostrophe would break out of the single-quoted YAML scalar the
API emits.

### The agent refuses to write a config it cannot complete

Missing credential key ⇒ print the names, **exit 3, leave the existing config untouched**. Writing a
partial config would produce a stream that fails to authenticate with nothing anywhere saying why —
and it would restart go2rtc, dropping every viewer of every *working* camera to install a broken one.

It also scans the YAML text itself for `{{cred:…}}` rather than trusting the API's declared list, so
a placeholder the API forgot to declare cannot survive into go2rtc as a literal.

### It only restarts go2rtc when the rendered file actually changed

A restart drops every viewer. The agent renders, compares, and exits early on no change — which is
why `Render` sorts by stream key: unstable ordering would restart the service on every run.

### The token is in a file, not the environment

`sud env VMS_API_TOKEN=… vms-sync` would put the token in the command line for every user on the box.
It reads `/srv/vms/gateway.token` (600, root) instead.

### go2rtc runs as its own user, sandboxed

`vms-go2rtc.service`: `User=vms`, `ProtectSystem=strict`, `ReadOnlyPaths=/srv/vms`, `NoNewPrivileges`.
`go2rtc.yaml` is `640 root:vms`; `credentials.env` is `600 root:root` and **the service cannot read
it** — verified. `base.yaml` disables go2rtc's own RTSP and WebRTC listeners and binds the API to
`127.0.0.1` only, which matters because **go2rtc's `/api/streams` echoes each source URL back with the
credential in it**.

## ⚠ A mistake I made, and the fix

Writing the two secret files, I used `printf pw | sudo -S tee <file>` — the pattern where sudo eats
the first line as its password and `tee` writes the rest. **When sudo's credential cache is already
warm it does not read stdin at all**, so `tee` wrote *both* lines: the VPS login password became line
1 of `credentials.env` and of `gateway.token`.

Caught by a length that did not add up — a 43-character token in a 48-byte file. Confirmed by dumping
both files with every character masked, which showed a 4-character first line in each.

**Fixed** by never piping data through `sudo`: build the file as the ordinary user under `umask 077`,
then `sudo install` it into place. Both files rewritten and verified by digest — the camera password
and the token match, and the login password is absent. Added to GOTCHAS.

## Proof

Run against the **real** API (started locally, reachable from the VPS over a reverse SSH tunnel, no
port exposed) reading the **real** `CeoDb` row from step 2, and the **real** camera:

| Check | Result |
|---|---|
| No token / wrong token | **401** both |
| Valid token | **200**, one camera, `credentialKeys: ["default"]` |
| Sync | wrote `/srv/vms/go2rtc.yaml`, restarted the service |
| go2rtc afterwards | serves `baneh-01`, **694 KB of video in 15 s (~370 kbit/s)** — matching the site's measured link |
| Second sync, nothing changed | *no change*, **not restarted** |
| **A camera added as a row**, credential missing | **exit 3**, config untouched, go2rtc still serving the old list |
| Credential added, sync again | both cameras in the config, go2rtc serves both |
| `vms` user reading `credentials.env` | **refused** |
| `vms` user reading `go2rtc.yaml` | allowed |
| Service restart | comes back, streams reload |

Tests: **unit 368 passed** (+9), **functional 186 passed / 3 failed** (+10) — the same three
pre-existing failures confirmed against a clean tree in step 2.

`The_wire_property_names_are_what_the_sync_script_reads` is worth calling out: `vms-sync.sh` is not
C# and reads those JSON names by hand, so renaming a DTO property would compile, pass everything
else, and break the sync on the VPS with a `KeyError` nobody is watching. Same class as the
snake_case Bale payload in GOTCHAS — only a test that reads real bytes can see it.

## Follow-ups

- **`/srv/vms/gateway.token` currently holds a throwaway value** generated for this test. Step 9 must
  replace it with `VMS_GATEWAY_TOKEN` from `deploy/.env` and set the matching `Vms__GatewayToken` on
  the API container. Until then no deployed API accepts it, which is the safe direction.
- **Nothing runs `vms-sync` automatically yet.** A systemd timer is the obvious answer, but the
  interval is a real decision — a sync is cheap, a restart is not, and the agent only restarts on a
  genuine change. Left for step 9 alongside the deploy.
- Still open from step 1: **is ~0.41 Mbit/s typical of every site?** Two or three more camera IPs
  would settle it, and it shapes step 6's grid.
