# VMS step 7 — one puller per camera, measured

- **Date:** 2026-08-02
- **Area:** VMS — `vms-web/src/features/wall`
- **Branch / commits:** `main`
- **Status:** **done.** The cap is in the SPA; the gateway half was measured rather than assumed.

## Criterion

> *Fullscreen = a bigger tile of the **same substream**, plus a one-viewer-per-camera cap. Done when
> no camera is ever pulled twice at once.*

Fullscreen already showed the same substream (step 6). This step is the cap — and, more usefully,
**checking a claim the design had been resting on since step 1 without evidence**.

## What was actually unproven

Everything since §2.3 has depended on "go2rtc holds *one* connection per camera and fans it out". It
was asserted, never measured. If it were false, the whole product would be wrong: the site has room
for one puller, so N viewers meant N starved streams.

Measured from inside the docker network, straight at go2rtc:

| | producers | consumers | bytes per viewer / 20 s |
|---|---|---|---|
| idle | 1 | 0 | — |
| one viewer | **1** | 1 | 352 778 |
| **four viewers** | **1** | 4 | 352 397 · 370 624 · 370 624 · 370 624 |

Two independent signals agree. The producer count stays at **one**, and — the check that does not
depend on trusting go2rtc's own bookkeeping — **each of four viewers got the same bytes as a single
viewer**. Four RTSP sessions sharing a 0.41 Mbit/s link would have given each about a quarter.

### And it lets go when nobody is watching

`producers=1` at idle looked alarming, because a camera held open with nobody watching would burn the
site's entire uplink around the clock. It is not a connection — it is the configured source:

| | producer fields |
|---|---|
| idle | `url` only |
| while one viewer is attached | `remote_addr = 78.39.233.70:554`, `bytes_recv`, `sdp`, `receivers`, … |
| 10 s after the last viewer left | `url` only again |

So the design's sentence — one connection while somebody watches, none when nobody does — is exactly
what happens.

## The cap in the SPA

go2rtc protects the *camera*. Nothing was stopping **this app** opening the same stream twice, and
each duplicate is VPS bandwidth spent twice for one picture. It happens for ordinary reasons: a tile
is on screen and somebody expands it, so the tile and the modal both want it while the modal is open.
React's StrictMode double-mounts every effect, which is the same problem a millisecond apart.

`streamLease.ts` — at most one connection per camera key per tab. **Last acquire wins**, and that
direction is deliberate: refusing the newcomer is the obvious rule and the wrong one, because during
a modal transition the new player mounts before the old one unmounts, so "first wins" would leave the
screen the user is looking at black while an invisible tile holds the lease.

The lease is the *guarantee*. The *mechanism* is that `CameraWall` suspends the tile whose camera is
expanded — because a preempted tile has no reason to reconnect when the modal closes, whereas
flipping `enabled` re-runs its effect and it comes back by itself.

## What is not covered

- **A second browser tab, or a second admin.** The lease is per tab. The camera is still safe — one
  RTSP session, proven above — but the VPS sends the stream once per viewer. At ~0.35 Mbit/s against
  44–62 Mbit/s of upload that is not a constraint, and pretending otherwise would mean coordinating
  state across tabs for no benefit.
- **The step 8 health sweep is a second puller.** It must skip any camera with a live consumer, and
  go2rtc's `consumers` count is exactly how to tell.
- **`streamLease` has no unit test.** No SPA in this repo has a test framework, and adding one here
  would set a convention in a single panel. Its behaviour is argued above; the property that matters
  — one pull per camera — is measured at the system level instead.
