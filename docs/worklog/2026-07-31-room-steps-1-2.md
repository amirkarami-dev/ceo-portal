## Goal
Start the room service at `room.myceo.ir`, ported from `vahedgas-portal/vnext/room-web`.
Step 1: a media server. Step 2: the meeting model and its rules.

## Step 1 — LiveKit on Amir's own VPS

The first draft of the design proposed sharing `vng-livekit`, which already runs on the ceo-portal box.
Amir offered a dedicated machine instead, and that is better for two reasons worth recording: a LiveKit
API secret is **not scoped to a room**, so sharing one server means either product could mint a token
into the other's meetings; and the ceo-portal box already runs **47 containers** on 8 cores, where video
is exactly the workload that will not tolerate a noisy neighbour.

Installed at `/srv/sites/livekit` on `185.182.220.182`:

- `livekit/livekit-server:v1.13.3`, `restart: unless-stopped`
- API key and secret **generated on that machine** — the secret was never transmitted or displayed
- Behind the box's existing Traefik v2.11 (`websecure`, `myresolver`, TLS-ALPN), host `lk.myceo.ir`
- Signalling on 7880 stays inside the docker network; only media (7881/tcp, 7882/udp) is published

### Three things that went wrong, and what they teach

1. **A UDP port range of size one makes LiveKit panic** — `port_range_start: 7882` with
   `port_range_end: 7882` crashes with `invalid argument to Intn` before the server ever starts. The
   single-port setup is `udp_port: 7882` (UDP mux), which is a different key entirely.
2. **`net.core.rmem_max` cannot be set per container.** LiveKit warns the UDP receive buffer is 425984
   against the 5 MB it wants. Raising it on the host did not reach the container, and putting it in
   `sysctls:` makes runc fail with `no such file` — *and took the container down until reverted*. Left
   as-is and documented in the compose file: it bounds **inbound** media, and a presentation has exactly
   one publisher. Revisit with host networking if large all-publish meetings appear.
3. **A heredoc attached to `sudo -S` steals stdin**, so the password never arrives and sudo just fails.
   Write the file first, then `sudo cp`.

### The blocker that mattered

The VPS holds `192.168.100.12` and sits **behind a home router**; the public address is the router. Only
forwarded ports arrive. Proof it was the router and not the box: ufw explicitly allowed 8080 and Traefik
published it, yet it was unreachable from outside. Amir forwarded 7881/tcp and 7882/udp (and 8080).

The difference is visible in LiveKit's own log, and it is the single line that says whether video will
work at all:

```
before:  could not validate external IP … context canceled → no external IPs found
after:   using external IPs {"ips":["185.182.220.182/172.18.0.12"]}
```

### Verified live
- `lk.myceo.ir` resolves to the VPS; Let's Encrypt certificate valid to 29 Oct 2026 (`ssl_verify_result: 0`).
- TCP 443 and 7881 reachable from the internet; **UDP 7882 round-trip proven** by the log line above.
- A hand-minted HS256 token: `ListRooms` → **200 `{"rooms":[]}`**, `CreateRoom` → **200** with a sid,
  `DeleteRoom` → 200. **A malformed token → 401.** Both halves matter: the server trusts what we sign
  and refuses what we do not.

### Bandwidth — measured, and lower than assumed
Amir estimated 500 Mbps. Measured from the VPS, twice each: **upload 44–62 Mbit/s** to Cloudflare
(international), ping to the Iranian datacentre **14 ms**. A domestic-throughput test was attempted and
was **invalid** — the endpoints used reject the body early — so no domestic number is claimed here.

At ~1–1.5 Mbit/s per viewer that is roughly 30–40 comfortable viewers, with LiveKit degrading quality
rather than failing beyond that. Worth re-measuring properly before any large event.

## Step 2 — the meeting model

- `src/Domain/Rooms/Room.cs` — `RoomType` (`Meeting` / `Presentation`), `RoomJoinMode`
  (`InviteOnly` / `Private` / `Public`), the join-link secret, presenter, start time and early-join
  grace. Two behaviours live on the entity: `MayPublish(userId)` and `IsOpenAt(now)`.
- `src/Domain/Rooms/RoomInvite.cs`, `RoomMessage.cs`.
- `src/Infrastructure/Data/Configurations/Rooms/RoomConfigurations.cs`.
- Migration `20260731110432_AddRooms`, applied locally.
- `tests/Application.UnitTests/Rooms/RoomTests.cs` — 12 tests.

### Decisions
- **The four type rules are CHECK constraints, not just validators.** Each is a security rule, so it is
  enforced where no code path can go round it:
  `Public ⇒ Presentation` · `Presentation ⇒ has a presenter` ·
  `InviteOnly ⇔ no join token` · `InviteOnly ⇒ Meeting`.
- **`MayPublish` is the real gate**, because the join token is built from it and the media server
  refuses a track the token does not allow. A tampered front end cannot switch an audience microphone
  on. It fails closed on a null identity and on a presentation with no presenter set.
- **The presenter match is `StringComparison.Ordinal`** — a near-miss identity must not publish.
- **`JoinToken` is the link secret, not the id**, with a filtered unique index. Regenerating it is the
  only way to kill a link that reached the wrong people.
- **The `ceo-` slug prefix stays** even on a dedicated server: a room name is the only thing a join
  token is scoped to, so an unprefixed name is one config change away from colliding with another
  product.

### Verification
- `dotnet test` — **262 unit passed** (+12), functional 72 passed / 3 failed (the same three
  pre-existing failures recorded in `2026-07-30-election-voter-flow.md`).
- **Against the real database**, every rule was exercised: two valid shapes inserted; four invalid ones

**Not verified:** nothing uses these tables yet — no API, no UI, and no media token has been minted from
