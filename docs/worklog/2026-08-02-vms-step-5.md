## The problem the design did not see

A `<video>` element and a WebSocket handshake **cannot carry an `Authorization` header** — the browser
builds those requests itself. So the bearer token the SPA holds is unusable for the only thing that
matters here.

What a browser does attach by itself is a **cookie**. So:

```
SPA ──bearer──► POST /api/VmsMedia/session   → Set-Cookie vms_media (.myceo.ir, HttpOnly, Secure, Lax)
browser ────────► https://cam.myceo.ir/...    (cookie attached automatically)
                        │
              Traefik ──┴──forwardAuth──► GET /api/VmsMedia/check → 204 allow / 401 refuse
```

`vms.myceo.ir` → `cam.myceo.ir` is **same-site** (one registrable domain), so `SameSite=Lax` is sent
and `None` — which would hand the cookie to any third-party page — is not needed.

The token is HMAC-SHA256 over `v1.<exp>.<subject>`, signed rather than stored: every tile, segment
and reconnect goes through forwardAuth, so a hash beats a database lookup, and there is no state to
fall out of step. It carries no camera scope, because authorisation here is one bit — administrator
or not.

## Three things about the VPS that the docs had wrong

1. **Traefik is a container, not a host service.** It runs with the **docker provider only**. Routing
   to a process on the host would have meant adding a file provider to the shared `traefik.yml` and
   restarting Traefik — which also fronts `lk.myceo.ir`, gitea, metabase and minio. Labels need no
   restart, so **go2rtc became a container**, and step 4's systemd unit was retired.
2. **Docker here is Docker Desktop under a user session.** `sudo docker ps` sees nothing, which for a
   few minutes looked like LiveKit being down. It is not: `ceo-livekit` is up and `lk.myceo.ir`
   answers 200. Root cannot reach the daemon, so `vms-sync` restarts the container via
   `runuser -l amirserver`.
3. **`cam.myceo.ir` already had its DNS pointed and grey**, so Traefik's TLS-ALPN challenge worked
   first time — a real Let's Encrypt certificate, valid to 31 Oct 2026.

## ⚠ The bind mount that silently mounts nothing

Docker Desktop bind-mounts only host paths on its sharing list. A path outside it **does not fail** —
it mounts as an **empty directory**, go2rtc starts on its defaults, and the only symptom is
`/api/streams` returning `{}`.

`/srv/vms` is not shared; the docker user's home is. Proven directly:

```
/home/amirserver/vms-config/probe.yaml -> 12        (read fine)
/srv/vms/base.yaml                     -> DIRECTORY
```

Two tells were visible before I understood it, and both are worth remembering: `/api/streams`
answered `{}`, and the log showed `[rtsp] listen addr=:8554` even though `base.yaml` sets
`rtsp.listen: ""` — go2rtc was running on defaults, which means it had read no config at all.

A second trap on top of the first: **Docker creates a missing bind-mount source as a directory.**
Once the container had started against a not-yet-existing `go2rtc.yaml`, that path *was* a directory,
so `install` then wrote the file **inside** it. The order matters — render first, mount second.

The generated config now lives at `/home/amirserver/vms-config/go2rtc.yaml`, `600` and owned by the
docker user. That is not a weakening: **the docker user controls the daemon and is root-equivalent
already**, so hiding a file from them buys nothing. Everything genuinely secret —
`credentials.env`, `gateway.token` — stays root-only in `/srv/vms`.

## ⚠ A mistake, the same family as step 4's

`sud() { printf pw | sudo -S "$@"; }` **replaces stdin**. So `sud tee <file> <<'EOF'` writes nothing —
the heredoc never reaches `tee`. It produced a 0-byte override file that quietly did nothing, and it
is the same root cause as step 4's password-in-the-file bug: *never pass data through `sud`*. Build
the file as the ordinary user, then `sudo install` it. Added to GOTCHAS.

## Residual risks, honestly

- **`/api/streams` returns the camera password to an authorised viewer.** go2rtc echoes each source
  URL, credentials included. It is now behind forwardAuth, but any administrator can read it. The
  player needs only `/api/ws`, `/api/stream.mp4` and `/api/frame.jpeg` — **step 6 should restrict the
  router to those paths** and leave `/api/streams` unreachable.
- **Every container on this box shares the one `traefik` network**, so a compromised neighbour could
  reach `vms-go2rtc:1984` directly and bypass forwardAuth. Fix is a dedicated docker network shared
  only with Traefik; not done because attaching Traefik to a new network touches the shared stack.
- The forwardAuth address is `https://api.myceo.ir/api/VmsMedia/check`, which **does not exist yet** —
  so today every request to `cam.myceo.ir` is refused with the 404 Traefik relays. Fail-closed, and
  the right direction until step 9.
